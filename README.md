# 1. Зачем нужна эта система?

Целью разработки этого проекта является увеличение эффективности банковской системы при работе с мошенническими транзакциями.

Это позволит:

- уменьшить **финансовые и репутационные риски**, связанные со штрафами за пропуск фродовых транзакций;
    
- уменьшить **отток недовольных клиентов**, чьи транзакции были ложно классифицированы как мошеннические;
    
- уменьшить **нагрузку на аналитиков**, которые вручную обрабатывают часть транзакций, засчитанных базовой системой как мошеннические.
    
Нужно было построить AntiFraud-проект, который показывает не только обучение классификатора,
но и то, как модель могла бы использоваться внутри сервиса.

---

# 2. Результат работы системы

Данная система будет классифицировать каждую транзакцию на предмет мошенничества.

Результат работы системы будет отслеживаться при помощи следующих трёх метрик:

- **Выгода от выполнения транзакций** — банк получает некоторую долю от выполненной транзакции.
    
- **Величина штрафа в конце месяца** — отражает суммарный размер штрафа, который получает банк в конце каждого месяца за пропущенные мошеннические транзакции. Успешная работа антифрод-системы должна уменьшать эту метрику.
    
- **Нагрузка на команду аналитиков** — отражает сумму, потраченную на работу команды аналитиков для ручной перепроверки части транзакций. Аналогично, успешная работа системы должна уменьшать объём транзакций, которые отправляются на ручную обработку.


Стоимость системы будет складываться из двух пунктов:

- затрат на работу команды специалистов, которая будет разрабатывать и поддерживать систему;
    
- затрат на инфраструктуру системы: облачные технологии, вычисления модели, обеспечение безопасности и т. д.
    

Ключевым критерием работы системы также является **скорость работы**.

Время обработки каждой транзакции не должно превышать некоторый порог $T$, чтобы не ухудшать клиентский опыт использования услуг банка.

Работа антифрод-системы будет считаться успешной, если выгода от её введения превысит стоимость затрат на её разработку через $N$ месяцев.

# 3. Как достигнуть поставленной цели?

В терминах машинного обучения это задача **бинарной классификации с сильным дисбалансом классов**. В качестве метрики для оценки качества решения подобных задач используем метрику **PR-AUC** - она показывает качество модели при разных порогах. Кроме того, она устойчива к дисбалансу классов.

С точки зрения бизнес-задачи нужно увеличить количество заблокированных фродовых транзакций, что соответствует метрике **Recall**.

При этом следует гарантировать минимальное количество ложных блокировок обычных транзакций, что соответствует метрике **Specificity**.

Кроме того, чтобы контролировать, какая доля поднятых системой операций действительно является fraud, для этого используется метрика **Precision**.

Поэтому в качестве метрики проверки качества модели машинного обучения стоит взять **Recall@Specificity**, которая позволяет максимизировать Recall при условии неухудшения Specificity. В качестве дополнительной проверки модели используется **Precision**.

Кроме того, для оценки модели используется набор аналитических метрик:
- **Fraud Amount Recall** - показывает долю суммы обнаруженных фродовых транзакций. Она важна, т.к. одна пропущенная операция на большую сумму может быть важнее нескольких маленьких.
-  **Review Rate** - показывает, какая доля операций отправляется на ручную проверку. Доля операций, которые можно просмотреть вручную, ограничена.
-  **Условная стоимость ошибок**: Total Cost Proxy = Missed Fraud Loss + False Block Cost + Review Cost.
   **Missed Fraud Loss** - сумма пропущенного fraud.
   **False Block Cost** - число ошибочных блокировок × условная цена блокировки,
       где условная цена блокировки - некоторое значение, которое вычисляется аналитически. В моем проекте я взял 10 × условная цена проверки.
   **Review Cost** - число проверок × условная цена проверки,
       где условная цена проверки - некоторое значение, которое вычисляется аналитически. В моем проекте я взял суточную зарплату аналитика в у.е., и поделил на          ожидаемое число транзакций, проверяемых в день одним аналитиком.

   Условная стоимость ошибок - это сценарная величина для сравнения моделей и порогов. Она не является реальной стоимостью fraud для банка. 

## Набор данных

Для обучения моделей машинного обучения был выбран открытый набор данных с платформы  Kaggle:

[https://www.kaggle.com/datasets/ealaxi/banksim1/data](https://www.kaggle.com/datasets/ealaxi/banksim1)

BankSim — синтетический датасет, в котором нормальное поведение генерируется на основе агрегированной статистики реального банка, а мошенническое поведение моделируется отдельно посредством заранее заданных fraud-сценариев.

|Column Name|Description|
|---|---|
|`step`|Единица времени: 1 step = 1 день. Симуляция охватывает 180 дней (180 шагов).|
|`customer`|Анонимизированный идентификатор покупателя.|
|`age`|Возрастная категория покупателя.|
|`gender`|Пол пользователя.|
|`zipcodeOri`|Анонимизированный идентификатор региона покупателя|
|`merchant`|Анонимизированный идентификатор продавца.|
|`zipMerchant`|Анонимизированный идентификатор региона покупателя|
|`category`|Категория транзакции.|
|`amount`|Сумма транзакции в симулируемой валюте.|
|`fraud`|Бинарный признак: `1` — транзакция является мошеннической, `0` — обычной.|

BankSim является синтетическим набором данных.
Поэтому даже хороший результат на нём нельзя напрямую переносить на настоящую банковскую
систему.

## Работа с данными

### 1. Предварительная обработка данных

Перед обучением модели выполняется анализ и подготовка исходного набора данных BankSim. Столбцы `zipcodeOri` и `zipMerchant` исключены, поскольку содержат единственное уникальное значение и не несут полезной информации для классификации мошеннических транзакций.

### 2. Временная организация данных

Поле `step` используется как временная ось транзакций. Оно необходимо для разделения выборок, построения исторических признаков и анализа изменения поведения клиентов и торговых точек во времени.
Поля `customer` и `merchant` нужны для группировки транзакций для построения исторических признаков.

Данные разделяются хронологически, без случайного перемешивания:

- **Обучающая выборка** — наиболее ранний период.
- **Валидационная выборка** — последующий период для подбора параметров модели и порогов классификации.
- **Тестовая выборка** — наиболее поздний период для итоговой оценки качества модели.

Границы периодов определяются на основании анализа временного распределения данных.

### 3. Формирование исторических признаков

Для повышения качества обнаружения мошенничества используются исторические характеристики клиентов и торговых точек. Они рассчитываются на основе предыдущих транзакций, хранящихся в PostgreSQL.

Для клиентов учитываются количество предыдущих операций, средняя сумма и её стандартное отклонение, время с последней транзакции, отклонение текущей суммы от среднего значения и наличие истории операций.

Для торговых точек аналогично рассчитываются количество операций, средняя сумма и её стандартное отклонение, время с последней транзакции, число уникальных клиентов, отклонение текущей суммы от среднего значения и наличие истории.

Дополнительно используются характеристики текущей транзакции и клиента:
 - сумму (`amount`);
 - категория возраста (`age`);
 - пол (`gender`);
 - категория операции (`category`).

Признаки `step`, `customer`, `merchant` напрямую в модель не передаются, так как могут служить источником переобучения модели.

### 4. Предотвращение утечки данных

Ключевое требование к обработке данных — исключение утечки информации из будущего. При формировании исторических признаков для транзакции с временным шагом `t` разрешено использовать только операции, для которых `step < t`.

Текущая транзакция и любые последующие операции не должны влиять на исторические агрегаты. Это предотвращает завышение качества модели при обучении и оценке.

Правила расчёта признаков должны быть единообразными для обучающей, валидационной и тестовой выборок, а также при обработке запросов через FastAPI. Это обеспечивает согласованность между обучением модели и её эксплуатацией в системе.

## Прогнозирование риска и принятие решений

### 1. Оценка риска транзакции

Модель возвращает числовую оценку `fraud_score` в диапазоне от 0 до 1. Чем выше значение, тем более подозрительной выглядит транзакция с точки зрения модели. Данная оценка характеризует относительный уровень риска и не интерпретируется как точная вероятность мошенничества.

### 2. Правила принятия решений

На основе оценки риска и двух настраиваемых порогов `T_low` и `T_high` система определяет действие:

- **ALLOW** — `score < T_low`: транзакция разрешается.
- **REVIEW** — `T_low <= score < T_high`: транзакция направляется на дополнительную проверку.
- **BLOCK** — `score >= T_high`: транзакция блокируется.

Модель отвечает за оценку риска, а отдельный компонент бизнес-логики — за выбор действия. Такое разделение позволяет изменять правила обработки транзакций без переобучения модели.

### 3. Выбор порогов классификации

Пороговые значения подбираются на валидационной выборке с учётом требований к качеству обнаружения мошенничества и допустимому количеству ложных срабатываний.

Верхний порог `T_high` определяет границу между дополнительной проверкой и блокировкой. Например, если допустимый уровень ложноположительных срабатываний (**FPR**) ограничен значением `0,5%`, выбирается порог, удовлетворяющий этому условию.

При выборе среди подходящих значений предпочтение может отдаваться порогу с более высоким **Recall** — долей обнаруженных мошеннических транзакций. При этом необходимо учитывать компромисс между обнаружением мошенничества и количеством ошибочных блокировок.

Порог `T_low` определяет границу между автоматическим разрешением и дополнительной проверкой. Настраивается с учётом требований к нагрузке на ручную проверку операций и условной стоимостью ошибок.

## Анализ ошибок модели

### 1. Цель анализа

Анализ ошибок проводится на тестовой части данных для оценки качества обнаружения мошеннических транзакций, выявления наиболее проблемных категорий и определения финансового объёма пропущенного мошенничества.

### 2. Анализ по категориям операций

Для каждой категории транзакций рассчитываются:
- **TP** — корректно обнаруженные мошеннические операции;
- **FN** — пропущенные мошеннические операции;
- **FP** — легитимные операции, ошибочно классифицированные как мошеннические;
- **TN** — корректно распознанные легитимные операции.

Дополнительно рассчитываются количество транзакций, доля мошеннических операций (**fraud rate**), доля пропущенного мошенничества (**FNR**), доля ложноположительных срабатываний (**FPR**) и доля суммы мошеннических операций, которую удалось обнаружить (**fraud amount recall**).

Категории сортируются по убыванию суммы пропущенных мошеннических операций. Это позволяет определить направления, в которых модель несёт наибольшие финансовые потери.

### 3. Анализ пропущенных мошеннических операций

Отдельно формируется список наиболее крупных пропущенных мошеннических транзакций. Для них сохраняются доступные идентификаторы и характеристики операции, включая время, клиента, торговую точку и признаки, использованные моделью, а также рассчитанный `fraud_score`.

Этот список позволяет исследовать случаи, в которых модель не обнаружила мошенничество, и выявлять возможные закономерности ошибок.

### 4. Визуализация и сохранение результатов

Результаты анализа сохраняются в MLflow в рамках текущего запуска эксперимента:
- агрегированная таблица ошибок по категориям в форматах JSON и CSV;
- список наиболее крупных пропущенных мошеннических операций в JSON;
- график со сравнением сумм обнаруженного и пропущенного мошенничества по категориям;
- общие финансовые метрики и метрики по отдельным категориям.

Таким образом, анализ ошибок дополняет стандартные метрики качества модели финансовыми показателями и позволяет оценивать не только количество ошибок, но и их потенциальное влияние на работу антифрод-системы.
